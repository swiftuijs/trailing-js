# RFC NNNN: Feature name

**Status:** Proposed.
**Kind:** Language / tooling.
**Release:** Not released.
**Dependencies:** RFC numbers, or none.
**Review:** RFC PR, acceptance decision and implementation PR when available.

## Problem and native baseline

Describe a recurring task and the error or maintenance burden. Include equivalent native TS/JS and the proposed improvement.

## Design

Define syntax/API, contextual recognition and ambiguities, types, scope, evaluation order, matching/exit behavior, errors and suspension. Mark examples as proposals until implemented. Separate initial scope from possible follow-up work.

## Lowering and interoperability

Show representative emitted TS/JS and declaration surfaces. Specify native-module boundaries, external values, configurations and required runtimes. Count allocations, reads, copies and scheduling.

## Compatibility and alternatives

Identify behavior changes and version/migration requirements, adjacent valid syntax, native alternatives and rejected designs with reasons.

## Validation and completion

List meaningful runtime and negative cases; type/checker/mapping behavior; formatter, lint, highlighting and real packaged editor support; build/loader/package/export checks and measurements. Link existing evidence for retrospective RFCs. Implementation completion requires the relevant evidence and documentation.

## Open questions and decision history

Record unresolved decisions, acceptance/rejection review links and subsequent amendments. Do not imply unreviewed proposals are accepted.
