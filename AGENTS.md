# Working on Twill

Twill is TypeScript/TSX with Swift-inspired syntax, compiling to ordinary JavaScript. Preserve native JS/TS behavior at documented boundaries and use the TypeScript type system. Keep frameworks and component libraries outside language semantics. Public documentation is English; maintain the existing hummingbird branding and link to the SwiftUI.js homepage when referencing the sibling project.

## Repository and environment

Follow root `package.json` engines and `packageManager`, and install with `pnpm install --frozen-lockfile`. The distributed packages support an older Node version than the repository tools. Canonical guides live in `docs/`; VitePress configuration lives in `apps/docs/.vitepress`. Repository-only RFC/contribution pages stay outside public navigation, search and sitemap. Start with [CONTRIBUTING.md](CONTRIBUTING.md) and its linked architecture/tooling guides for detailed workflows.

Tests, fixtures and test dependencies belong to the owning package. Shared TextMate sources belong to `packages/highlight/grammars`; keep the shipped copies in `editors/vscode/syntaxes` identical. Preserve unrelated working-tree changes and keep PRs focused.

## Develop tooling in Twill

Use `.twill` / `.twillx` for handwritten production sources in packages and editor integrations outside `packages/twill`. Native TypeScript is valid Twill; prefer extensions only when they clarify code and preserve efficient native output. Fix compatibility problems in the compiler with regression tests rather than renaming public APIs or weakening checks. Update source imports to the actual `.twill` / `.twillx` paths.

Build through public Twill adapters, check with `twill check`, and emit ordinary consumer declarations with `twill declarations`. Keep compiler dependencies development-only where consumers do not need them. Preserve public JS exports, source maps, complete original-source coverage, independent consumers and existing performance/size gates. `pnpm verify:dogfood` rejects native implementation files in package/editor `src` directories, including new packages; release verification runs it before builds.

Bootstrap exceptions are explicit: the compiler/parser remain JS/TS; `packages/runtime` keeps the canonical JS helper used before compiler build; Rust keeps the native subprocess engine. Build/configuration/release/install scripts and native interoperability test harnesses stay in host-supported formats. Vue SFCs and their documentation-app support code retain native sources until Twill integrates with that host's type checker. Tests may mix native and Twill inputs to exercise both boundaries. Document a concrete host/bootstrap reason when adding an exception, and update the verification policy with it; do not silently skip a package.

## Language and tooling changes

Write or amend an independent RFC before introducing Twill syntax, semantics or a public tooling capability. Existing native JS/TS behavior needs no new RFC. Record the native baseline, evaluation order, binding/control-flow ownership, errors, suspension, interoperability and generated costs. Acceptance, implementation, merging and publication are separate statuses; keep the guides honest about shipped versions and source prototypes.

Compare performance-sensitive output with equivalent natural handwritten JS. Preserve native fast paths and avoid unnecessary closures, wrappers, helper imports, copies or scheduling. Measure runtime and bytes separately, retain all samples and source/build identities, and do not claim a general speedup from noisy synthetic timings. Do not relax tests, coverage or size gates to conceal a regression.

## Feature synchronization checklist

Every new feature, public API or semantic change, compatibility fix, performance change and removal requires a review of all surfaces below. Identify affected surfaces before implementation and update their implementation, regression tests and user guidance in the same PR. Before marking the PR ready, record the changes and validation for each affected row; give a concrete reason for each unaffected row. An unchecked surface is unfinished work. Do not add unrelated behavior just to fill the checklist.

| Surface                  | Required review                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Language and output      | Parser/compiler, checker, source mappings, declarations and checked native export; preserve evaluation order, ownership, errors and adjacent native JS/TS behavior.                                                                                                                                                                                                                                           |
| Tooling and integrations | Formatter/idempotence, lint/fix safety, highlighting and shipped grammar copies, editor completion/navigation/rename/debugging, configuration, bundlers, loaders, docs playground and optional runtime helpers/ABI.                                                                                                                                                                                           |
| Executable scripts       | Twill CLI/runner, direct invocation and shebangs, literal argv, script-local imports/configuration, source errors, exit status and compiler-cache invalidation. Exercise applicable language features in actual scripts and exported JS.                                                                                                                                                                      |
| Shell API and engine     | `packages/shell` and `packages/shell-native`, public exports/types, shared commands/policies/error identities and real-process contracts. Review the SDK and Rust engine even for compiler-only changes; explain when native process execution is unaffected. Shared API changes must update the SDK, Rust boundary and real-process contract suite together; document platform-specific behavior explicitly. |
| Examples and consumers   | Relevant examples and fixtures, mixed Twill/TS/JS projects, declarations/export consumers and independently installed archives on the minimum supported Node version; exercise actual tools and processes.                                                                                                                                                                                                    |
| User guidance            | Root and affected package READMEs, relevant canonical `docs/` guides (including scripting, syntax, tooling, compatibility, installation and performance), RFC status, changelog and `skills/twill/SKILL.md`. Review examples, links, platform limits and published/source-only version boundaries; regenerate website skill downloads/discovery from the canonical source when it changes.                    |
| Delivery and validation  | Package exports/dependencies, manifests/lockfile, runtime/native protocol compatibility, CI/platform jobs, docs deployment triggers, OS/CPU/libc selection and all validated prebuild targets, artifact assembly, budgets and release instructions. Keep implementation, merging and publication statuses distinct.                                                                                           |

Shell changes also review literal argv/PATH, cwd/environment snapshots, stdin and both output streams, byte limits, status/error mapping, abort/timeout races, graceful/forced teardown, worker/process-exit cleanup and owned-child/descriptor lifetimes. Run the public SDK real-process suite on every supported target and keep Rust/loader-specific tests with their owning package. The SDK has one Rust execution backend; do not reintroduce Node execution or user backend selection. The native package is its implementation dependency and must not depend back on the SDK. Platform-sensitive changes require actual supported-platform/CPU/libc and independently installed Node consumers; validate Linux glibc and musl separately and Windows ARM64 with native ARM64 Node, and never equate cross-compilation with support; performance-sensitive changes retain equivalent handwritten Node comparisons, all samples and source/build identities. Compiler/runner changes review language support in shell scripts and cache invalidation without assuming that a Rust subprocess addon needs compiler semantics.

Keep the SDK's 16 KiB archive budget and compiler independence separate from the native dependency's 2 MiB binary / 6 MiB archive gates and optional language-runtime costs. Preserve deterministic correctness, coverage and size gates. Follow the [testing](docs/contributing/testing.md) and [release](docs/contributing/releasing.md) guides for applicable commands; record unsupported or deferred behavior rather than implying support in documentation or the official skill.

CI may omit unaffected platform jobs for ordinary PRs using the complete base-to-head diff. Native/shared-shell/dependency/build changes require all eight targets; unknown paths or unavailable history select full validation. Main, scheduled, manual and release runs remain full. Documentation-only checks still validate skill/downloads, coverage and root/subpath browsers. Cache compilation inputs by OS/CPU/libc/toolchain, never use a cache hit as a passed test, and preserve the required `verify` check when changing CI routing.

## Official skill synchronization

`skills/twill/SKILL.md` is the canonical portable application-development skill. Root `AGENTS.md` governs development of Twill itself; do not package repository-maintenance instructions as application requirements.

For any public syntax, semantic, tooling, compatibility, performance or release change, read the skill and update affected instructions/examples/version boundaries in the same PR. If the change does not affect guidance, state why in the PR. Never infer support from an RFC or PR title: default to published capabilities and explicitly distinguish source prototypes. A release version change requires reviewing the skill's `metadata.release` baseline along with user guides.

Website skill files and discovery metadata are generated by `apps/docs/scripts/prepare-skills.mjs`. Edit the canonical source, never those generated copies. `pnpm verify:skills` checks metadata/links, skill example types/execution and formatting. `pnpm docs:build` regenerates the exact download and digest; docs dev prepares them too. Update [AI assistance](docs/ai.md), the installation guide and this policy when installation or activation workflows change.

## User-facing setup guides

Review onboarding from an empty application directory and from an existing project. For each executable example, state prerequisites, which package supplies the command/API, installation scope, file location, the run command and expected output. Distinguish global CLI PATH from script-local dependency resolution, and execution from type checking. Provide npm and pnpm paths or link to an explicit command mapping; a shebang alone is not an installation guide. Keep contributor-only source-build commands out of user quickstarts. Connect standalone feature pages to the installation guide and relevant next step, and remove stale release/prototype labels when describing shipped behavior. Validate changed setup commands with independently installed published packages when practical.

## Validation and delivery

Run focused owning-package tests while iterating, then the checks appropriate to the final change. Language/mapping changes need execution and negative cases, adjacent native syntax/nesting, real original-source editor positions, and relevant independent package/browser/VSIX validation. Follow the existing CI and [testing guide](docs/contributing/testing.md); never replace an actual adapter, browser or packaged editor with a mocked check of the changed implementation.

For skill/docs changes run `pnpm verify:skills`, `pnpm format:check`, docs build/typecheck and relevant browser tests, including raw download/discovery and subpath hosting. Keep package manifests and the lockfile synchronized when changing dependencies. Release validation and skill checks run in CI; update contribution/release instructions when their workflow changes.

Create reviewable PRs that explain final behavior, scope, validation and measured limitations. Use the user's existing authorization for delivery actions; do not equate an implementation request with publication or merging unrelated work.
